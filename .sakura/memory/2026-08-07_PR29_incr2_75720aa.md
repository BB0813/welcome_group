## 2. 发现的模式

### 代码模式
- **"三个相似命令"的反模式**：项目用三个独立函数实现测试命令，触发本次重构。这暗示 `welcome_group` 类可能存在**"按事件类型分支"的设计惯性**——即每个事件（入群/退群/被踢）都有独立的处理函数 + 独立的测试命令。如果未来增加"管理员变更"等事件，会复制同样的三分支结构。
- **公共逻辑下沉到 `_run_test()`** 是典型的 Template Method 模式应用，但抽取时**没有把"差异化参数"完全参数化**（只传了 `llm_prompt`，没传语气词），导致 LLM 提示语硬编码丢失差异化——这是常见的**"重构时参数抽取粒度不够"反模式**。

### 架构观察
- **配置驱动的模板系统**：`self.config["default_message"]` 系列字段 + `{user_id}/{time}` 占位符替换，简洁但缺乏校验
- **LLM 与模板的回退关系**：模板为空时启用 LLM（推测自 `_get_message_template` 实现），这是常见但需要小心设计的双路径
- **命令注册器的限制**：PR 描述提到"命令注册器不支持嵌套 command_group"，这是 NoneBot/类似框架的常见约束，迫使命令命名从 `/leave test` 变成 `leave_test`——这种**框架约束导致的命名妥协**应在文档/README 中明确说明，避免用户困惑
- **快速审查策略**下，PR 平均涉及 +58/-87 行的中等规模重构，给出 7/10 + request_changes 是合理的"温和拒绝"信号

## 3. 规范完善建议

### 建议新增的审查规则

**规则 R1：重构时必须参数化所有差异化维度**
> 当提取公共辅助函数时，所有调用方原本"不同"的语义（包括语气词、错误文案、日志标签）都应作为参数传入，而非硬编码到辅助函数内。
> 
> 检查方法：对比重构前各调用点的"非常规差异"是否被参数化。

**规则 R2：重构必须验证"行为等价性"**
> 重构不仅是代码组织变化，更应是行为不变的保证。除非明确标注为行为变更，否则应：
> 1. 对比重构前后的对外可观测行为（消息文案、LLM 提示、日志、错误信息）
> 2. 确认配置读取的容错行为未变化（`.get()` vs `[]` 是常见回归点）

**规则 R3：命令重命名/重构必须同步更新所有引用**
> 命令名变更时，搜索以下位置并同步：
> - README.md 及 docs/
> - issue/PR 描述
> - 注释、docstring
> - CHANGELOG（如有）
> 
> 可在 PR 模板中加 checklist：`[ ] 已同步更新文档`

**规则 R4：增量审查必须对比前一版本的"问题清单"**
> 增量审查开始时，先列出"前一轮审查提出但未修复的问题"和"前一轮已修复的问题"，再开始评估本次变更。

### 项目特有规范要点

- **测试命令的"真实性"原则**：测试命令应 1:1 复现真实事件路径，包括 LLM 提示语措辞。建议在 `_get_message_template` 旁提取一个 `build_llm_prompt(event_type, user_id)` 供真实路径和测试路径共用，杜绝差异化丢失
- **`.get()` 默认值的红线**：项目若允许用户手工编辑 `config.json`，所有 `.get(key, "")` 类调用都应在调用点或辅助函数内做"空值校验 + 用户可见错误"

## 4. 经验教训

### 未来审查应关注的要点

1. **"重构提交"的最大风险不是新 bug，而是行为回归**。审查重构时应主动比对"前一行 vs 这一行"的语义差异，而不是只看代码是否更"漂亮"。
2. **抽取辅助函数时必查"被消除的字符串字面量"**——尤其是错误信息、日志标签、提示语、注释。`grep "f\""` 或 `grep "str literal"` 是好工具。
3. **`.get(key, default)` 是配置读取的"温和杀手"**，配置损坏时表现成"功能正常但内容空白"，比直接抛 `KeyError` 更难排查。建议团队规范：**配置读取一律 `[]`，让损坏快速暴露**；或在 `.get()` 后立即校验空值。
4. **文档同步是 PR 完整性的硬指标**。建议在 CI 中加一个简单的"命令名交叉验证"脚本（解析 README 中的命令提及，与代码中注册的命令对比）。

### 对特定技术/模式的审查经验

- **Template Method 模式抽取**：常见误区是"参数化不彻底"——把"骨架"抽走了，但把"血肉"硬编码在辅助函数里。审查清单：调用方原本的"差异点 X"在重构后是否仍可控？
- **NoneBot 类命令注册器**：命令命名是用户契约，重命名时应视为 API 破坏性变更（即使技术上不破坏），需走 deprecation 流程或在 README 显著提示。
- **LLM 提示工程代码**：提示语属于"软代码"——语法对即可，但语义（措辞、语气、上下文）对生成质量影响巨大。审查时应像对待文案一样对待提示语，不能因为它是字符串就略过。
