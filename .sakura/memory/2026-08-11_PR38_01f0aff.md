## 3. 规范完善建议

### 新增规则：Quick 审查中的框架 API 变更说明

| 检查项 | Quick 审查要求 |
|--------|----------------|
| 全局扫描是否执行 | **必须说明**："已扫描"或"未执行" |
| 风险评估 | 明确是否需要 full 审查补充验证 |
| 影响范围声明 | 与当前变更点分开，列出"可能存在但未覆盖"的同类调用 |

**理由**：Quick 策略允许范围限定，但框架 API 变更有扩散性风险，审查者应明确自己的边界在哪里。

### 修改规则：Comments 信息来源标注

**当前**：
```markdown
[comment]: 根据项目知识文档，这种差异是有意为之
```

**建议**：
```markdown
[comment]: 根据项目知识文档推断（置信度：0.7），这种差异是有意为之
         建议验证：是否可补充 _run_test 的调用路径说明？
```

## 4. 经验教训

### 值得关注的要点

1. **框架 API 变更 ≠ 只改一处**
   - 即使本次修复点明确，也要明确说明"全局扫描"的状态
   - "quick"不等于"可以忽略扩散风险"，需要在结论中显式声明边界

2. **"有意为之"的表述需谨慎**
   - 如果依赖文档而非代码，应降低置信度标注
   - 建议格式：`[推测/推断/待验证] + 置信度`

3. **测试代码的差异处理**
   - 本次发现测试命令与事件处理器使用不同 API
   - 这种模式值得记录：未来框架升级时，测试代码也需要同步检查

### 对特定技术的审查经验

| 技术点 | 本次经验 |
|--------|----------|
| AstrBot generator handler | `yield chain_result` vs `await send()` 的区别要明确记录 |
| MessageChain 类型一致性 | 确保 `message_list` 构建路径类型可控 |
| 版本号精确度 | PR 描述已做到 `v4.27.2` 精确标注，值得保持 |
