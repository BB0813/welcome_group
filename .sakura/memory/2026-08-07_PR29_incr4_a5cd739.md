## 4. 经验教训

### 值得在未来审查中关注的要点

1. **"重提交"场景的判定**：本次增量提交的 commit `a5cd739e` 与上轮审查的 `75720aa` diff 完全相同，这可能意味着：(a) PR 被要求重提交但代码未变，(b) CI 触发了重新生成，(c) 开发者合并后又 cherry-pick。审查时需要追问原因，否则会重复审查成本
2. **LLM 风格参数的可控性**：把风格写成硬编码字符串是临时方案，长期看应允许配置化（这是 R-AUTH 思路的延伸——可配置即意味着需要校验）
3. **"无新增评论"≠"无问题"**：本轮主要评论为空，但这是因为沿用上轮结论。审查流程上应在"无评论"时加一句声明，例如"本轮无新增问题，沿用上轮 X 条 Suggestion"，让 PR 作者知道不需要再处理

### 对特定技术或模式的审查经验

- **LLM 参数化重构**：除了关注参数本身，还要关注 prompt 工程的合理性（孤立形容词 vs 完整指令）
- **AstrBot/NilBot 类框架的命令注册**：命令名一旦注册很难平滑变更，命名妥协应在首次设计时就文档化
- **README 的"框架限制说明"**：这种描述容易过时（框架升级可能解除限制），应在文档里加版本标注或 TODO 标记
