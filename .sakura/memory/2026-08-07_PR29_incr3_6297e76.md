## 2. 发现的模式

### 代码模式
1. **f-string 习惯性使用**：开发者倾向于统一加 `f` 前缀，即便无占位符。这是个轻量风格问题，但说明可能缺乏 lint 工具约束（如 `flake8` 的 `F541` 或 ruff 的 `F541`）。
2. **LLM 调用模板构造**：使用 `f"..."` 内联拼接 `llm_prompt` + `llm_tone`，简单直接但缺乏类型安全——若 `llm_tone` 为 `None` 或空串，会拼出"要求。"的诡异文案。建议考虑参数校验。
3. **事件驱动 + 防御性早返回**：`yield event.plain_result(...)` + `return` 是 NoneBot 风格的惯用法，与项目其他部分一致。

### 架构观察
- 项目采用 NoneBot 框架，命令注册不支持嵌套 `command_group`，这是 issue #28 中 `leave_test` / `kick_test` 命名妥协的根源
- 测试命令与生产命令复用 `_run_test()` 核心逻辑，参数化做得较好（`llm_tone` 透传）
- 模板配置（`/welcome set`）与事件触发解耦，模板为空时的事件处理路径刚开始建立防御机制

## 3. 规范完善建议

建议在本项目沉淀以下审查规则：

| 规则 ID | 规则描述 | 适用场景 |
|---------|---------|---------|
| `PM-F541` | f-string 必须包含至少一个 `{...}` 占位符 | 所有 Python 文件 |
| `PM-EVENT-EMPTY-TEMPLATE` | 事件处理器在读取模板/配置后必须有空值校验，避免向群内发送空白消息 | `main.py` 所有事件分支 |
| `PM-LLM-PROMPT-INJECTION` | LLM 提示语构造时，用户可控字段需明确边界（如前后缀模板化） | LLM 相关调用 |
| `PM-README-COMMAND-SYNC` | README 中列出的命令名必须与代码注册名完全一致 | 修改命令注册时 |
| `PM-INCREMENTAL-MAPPING` | 增量审查必须显式列出"上轮意见 → 本轮修复"对照 | 所有增量审查 |

**项目特有规范要点：**
- 命令命名需避开 `command_group` 嵌套限制
- 测试命令与生产命令共享核心函数时，参数透传需保持完整
- 群消息发送前的校验应当成为标准实践（结合本次修复建立的模式）

## 4. 经验教训

### 值得在未来审查中关注的要点
1. **增量审查要建立"意见闭环"**：每条上一轮建议都应在本次审查中明确标记 ✅ / ❌ / ⚠️，避免遗漏
2. **f-string 冗余是个高频轻量问题**：建议配置 ruff `F541` 自动检测，可减少人工审查负担
3. **README 与代码一致性是常见的"文档债"**：本次修复后，应在 PR 模板中加入"修改命令时同步 README"的勾选项
4. **空模板防御是群机器人特有风险**：相比普通 Web 应用，群内空白消息更难被即时发现，应作为高优先级审查项

### 对特定技术或模式的审查经验
- **NoneBot 事件处理**：审查时关注 `yield event.xxx_result(...)` 后是否正确返回/继续，特别注意异常路径
- **LLM 集成**：提示语拼接处易出现注入或语义模糊问题，本次 `llm_tone` 直接拼接是简化但可接受的做法，若未来支持用户自定义 tone，需考虑白名单
- **参数化重构**：当重构引入新参数时，需审查所有调用点是否同步更新——本次增量修复了三个调用点，但应警惕未来扩展时遗漏
