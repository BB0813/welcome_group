## 6. 经验教训

### 本次分析不足之处

| 问题 | 严重程度 | 说明 |
|------|----------|------|
| 可行性评估空泛 | 高 | 应强制要求"至少给出推测性实现方向" |
| 重复检测使用模糊措辞 | 高 | "可能"属于无效结论 |
| 标签遗漏 `feature-request` | 中 | 影响 Issue 可发现性 |
| `good-first-issue` 置信度偏高 | 中 | 需求细节不足时不适合高置信度 |

### 未来应坚持的原则

1. **信息匮乏 ≠ 分析空缺**
   - 即使只有一句话，也要给出"推测性配置结构"
   - 可行性判断可写"基于假设，需确认"

2. **重复检测必须具体**
   - 对比维度：标题/功能描述/实现方式
   - 无法确认时明确写"需维护者核实"

3. **标签覆盖需检查**
   - enhancement 类 Issue 应优先考虑 `feature-request`
   - 配置相关项目加 `configuration`

4. **适用本仓库的特定经验**
   - 单文件架构 → 改动范围易于界定
   - 配置驱动 → 重点关注 `__init__.py` 中的 `Config` 定义
   - 回退逻辑 → 需明确"全局启用"与"独立配置"的优先级

### 建议追问用户的问题

```
1. 全局配置的默认欢迎语内容是什么？（空/预设模板/禁用？）
2. 独立群配置与全局配置的优先级：群配置存在时是否完全覆盖全局？
3. 是否需要在 AstrBot 插件配置页面暴露这些全局配置项？
```
