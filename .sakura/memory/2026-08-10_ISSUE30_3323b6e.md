## 六、经验教训总结

### 6.1 Issue 分析必须遵守的底线

| 原则 | 说明 |
|------|------|
| **信息不足 ≠ 可以猜测** | 当 Issue 缺少复现步骤、环境信息、预期 vs 实际行为时，应请求补充而非强行分析 |
| **区分用户问题 vs 代码问题** | 若根因可能是用户未正确配置，应标注为 `needs-info` 或 `question`，而非直接判定为 bug |
| **置信度应反映信息完整度** | Issue 信息越少，置信度越低，不能因为"常见问题"就高估 |

### 6.2 特定类型 Issue 的分析要点

**Bug 类 Issue**：
- 必须追问：用户是否尝试过基本排查（重启、重新配置、查看日志）？
- 若无 → 建议标记 `needs-info`
- 若有 → 重点关注分析中的"根因清单"是否覆盖了常见失误

**功能性 Issue（如本例）**：
- 优先验证"用户是否正确启用了功能"（`/welcome on`）
- 其次验证"Bot 是否正常接收事件"（检查事件过滤器）
- 最后才排查"模板/变量"等细节

### 6.3 对仓库项目的专项建议

根据项目记忆，该项目：
- 配置驱动 → 很多"bug"可能源于用户配置错误
- 单文件简单架构 → 模板变量不匹配等问题容易排查
- LLM 集成有 fallback → 应确认欢迎语生成失败时是否有降级

**针对性策略**：分析该仓库 Issue 时，应优先验证**配置状态**和**命令执行情况**，再深入代码层面。
