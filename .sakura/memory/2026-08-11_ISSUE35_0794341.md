# Issue 分析深度反思

## 1. 分类与优先级准确性

**评估**：基本合理，但存在关键信息不一致问题

| 方面 | 分析 |
|------|------|
| 分类 | ✅ `bug` 正确，模板变量未替换属于功能失效 |
| 优先级 | ✅ `medium` 合理，影响特定语法用户，非全局失效 |

**但存在严重的信息不一致**：
- 标题写的是 `{{at}}`（双大括号）
- 摘要写的是 `｛at｝`（全角括号）
- 原始内容写的是 `｛at｝`（全角括号）

这种不一致会导致后续开发者在代码中找不到正确的匹配模式。**分析时应统一原文表述，并明确指出用户使用的是 `｛at｝` 而非 `{{at}}`**。

## 2. 标签推荐质量

**评估**：标签选择正确，置信度校准存在偏差

| 标签 | 置信度 | 评价 |
|------|--------|------|
| `bug` | 0.9 | ⚠️ 偏高，应降至 0.7-0.8 |
| `good-first-issue` | 0.8 | ⚠️ 偏高，应降至 0.6-0.7 |

**置信度偏高的原因**：
1. 原文中括号样式存在不一致（`{{at}}` vs `｛at｝`），尚未确认代码实际支持的语法
2. 未确认 `{at}` 是用户自创语法还是文档推荐语法
3. 如果代码本身只支持 `{{at}}`，那这可能是**文档/用户教育问题**，而非代码 bug

**建议**：增加 `needs-info` 标签，要求用户确认：
> 请确认文档/配置中推荐的变量占位符格式是什么？是 `{{at}}` 还是 `{at}`？

## 6. 经验教训

### 6.1 信息不一致处理
当 Issue 中存在明显的信息不一致（如标题写 `{{at}}`，正文写 `｛at｝`），应：
1. **明确指出不一致**
2. **要求用户确认实际使用的语法**
3. **不要自行假设哪种是"正确"的**

### 6.2 模板变量类 Issue 的分析要点
```
□ 确认代码中定义的正则表达式模式
□ 确认用户实际使用的占位符格式
□ 区分"代码 bug"还是"文档误导用户"
□ 检查是否有大小写敏感性（如 {At} vs {at}）
```

### 6.3 本次分析的核心改进点
1. **降低置信度**：从 0.9 降至 0.7，更谨慎
2. **增加 `needs-info` 标签**：要求确认用户语法
3. **标题改写保留关键信息**：中文全角括号不应删除
4. **可行性判断前先验证假设**：不要在未读代码前做确定推断
