## 一、框架 API 兼容性修复审查规范 ⭐

### 1.1 必检清单

```
框架 API 变更审查检查清单
├── 版本号精确性
│   ├── [x] 精确到 patch (如 v4.27.2)
│   └── [ ] 说明影响起始版本
├── 全局影响评估
│   ├── [ ] grep event.send() 调用点
│   ├── [ ] grep MessageChain 构建点
│   └── [ ] 评估框架注入行为的触发范围
├── 兼容性策略
│   ├── [x] fallback 机制
│   ├── [ ] 版本判断逻辑（如需要）
│   └── [ ] API 能力检查（hasattr）
└── 测试覆盖
    └── [ ] 建议补充框架版本兼容性测试
```

### 1.2 核心规则

| 规则 | 触发条件 | 要求 |
|------|---------|------|
| **全局扫描声明** | 框架 API 绕过时 | 必须执行 `grep -r "event.send" --include="*.py"` |
| **注入行为扩散评估** | 框架自动注入组件时 | 评估注入行为的触发范围 |
| **PR 描述一致性验证** | PR 声称"移除 X"时 | 必须 grep 确认代码中是否真的不再使用 X |
| **版本影响边界说明** | 框架兼容性修复 | 明确说明从哪个框架版本开始受影响 |

### 1.3 Quick 策略局限性声明

Quick 策略应明确说明"未覆盖范围"：
```
本次审查未覆盖：
- 异常处理完整性
- bot 对象为 None 的日志记录
- 框架注入行为的全局影响评估
```

## 二、PR 描述一致性验证 ⭐⭐

### 2.1 危险信号识别

当 PR 描述说"移除 XXX"但代码仍在使用时，这是**高风险信号**：
- 多轮修改，部分修改未同步到描述
- 存在遗漏的回退路径
- 作者意图与实际实现有偏差

### 2.2 验证流程

```
1. grep -n "目标符号" 文件   # 定位所有使用点
2. 检查 import 语句          # 确认是否在导入列表
3. 分析使用场景              # 是否确实需要
4. 对照 PR 描述              # 是否与声明的变更一致
```

### 2.3 PR 描述陷阱

| 陷阱 | 风险 | 应对 |
|------|------|------|
| 描述"移除 X"但代码仍使用 | 高 | 必须 grep 确认是否真的移除 |
| 描述"修复 Y"但未展示关键代码 | 中 | 要求补充代码片段对比 |
| 描述与实现存在多版本差异 | 高 | 明确指出不一致，要求澄清 |

## 三、增量审查规范

### 3.1 Fallback 健壮性检查

多层 Fallback 审查清单：
- [ ] 验证每个路径的可用性假设
- [ ] 检查前置条件是否满足
- [ ] 评估 fallback 触发频率和影响

### 3.2 `getattr(obj, attr, None)` 审查重点

```
1. default 值为 None 时，后续是否有显式检查？
2. None 时是否有日志记录？
3. 是否有其他 fallback 路径？
```

### 3.3 绕过框架 API 的审查要点

| 检查项 | 说明 |
|--------|------|
| bot 对象可用性 | `getattr(event, 'bot', None)` 返回 None 的场景是否覆盖 |
| API 版本约束 | 目标版本是否支持该 API，是否需要 fallback |
| 异常处理 | 网络错误是否被捕获和处理 |
| 长期影响 | 规避方案是否丧失框架层封装优势 |

## 四、外部依赖/框架问题 Issue 分析模板 ⭐

### 4.1 责任边界模板

```
1. 明确责任归属：[框架]/[插件]/[用户配置]
2. 上游渠道：[框架 GitHub Issue 链接]
3. 插件侧应对：
   - 短期：[说明情况，等待修复]
   - 长期：[考虑内置 fallback 方案]
4. 用户引导：[手动安装/降级版本建议]
5. 跨仓库协作：[明确标注需等待框架修复，给出框架仓库链接]
```

### 4.2 必加标签

| 标签 | 适用场景 | 置信度 |
|------|----------|--------|
| `external-dependency` | 根因不在本仓库 | 0.95 |
| `regression` | 有版本号变化暗示（框架升级引入） | 0.6-0.8 |
| `needs-upstream-fix` | 插件侧无法独立解决 | 0.9 |
| `bug` | 运行时错误 | 0.95 |

### 4.3 标签使用纠正

| 错误用法 | 正确用法 |
|----------|----------|
| `framework-compatibility` | `external-dependency` 或 `regression` |
| 框架自身 bug 时使用 `framework-compatibility` | 应使用 `external-dependency` + `needs-upstream-fix` |

### 4.4 重复检测要求

- 必须说明搜索的关键词和范围
- 框架问题应搜索框架侧 Issue（如 AstrBot 主仓库）
- 结论应有依据支撑

│    _send_group_msg() → bot.send_group_msg() [主路径]     │

│                                                          │
│ 2. 防御性检查                                            │
│    hasattr(bot, 'send_group_msg')                        │
