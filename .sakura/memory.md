# 代码审查经验记忆

> 累计反思 15 次，持续更新中...

## 一、框架兼容性修复审查规范

当修复涉及第三方框架 API 变更（如 AstrBot）时，必须遵循以下检查项：

| 检查项 | 要求 |
|--------|------|
| 框架版本号 | **精确到 patch**（如 v4.27.2，而非 v4.27.x） |
| API 变更 scope | 明确影响哪些方法（如 `event.send()` 参数契约变化） |
| 向后兼容性 | 评估是否需要版本判断逻辑 |
| 全局扫描 | `grep` 全项目同类调用，确保无遗漏（quick 策略也建议检查） |

**必须添加的标签**：
- `framework-compatibility`：框架 API 变更类问题
- `regression`：若确认是版本升级引入的问题

**禁止表述**：
- ❌ "符合 v4.27.x API 规范" → ✅ "符合 v4.27.2，实测于 v4.27.3"

## 二、审查策略边界定义

| 策略 | 验证范围 | 必须在总结中注明 |
|------|----------|-----------------|
| quick | 修复点 + 直接影响范围 | "仅验证修复点，未做全量回归" |
| full | 修复点 + 间接影响 + 模式分析 | "含回归建议" |

**quick 策略的矛盾与平衡**：
- 优点：聚焦修复点，效率高
- 风险：若存在未发现的同类问题，评分可能过于乐观
- 建议：对于框架 API 变更类修复，即使 quick 也建议 `grep` 全局同类调用

## 三、Issue 分析质量规范

### 标签推荐完整性

| 缺失标签 | 理由 |
|----------|------|
| `framework-compatibility` | 涉及框架兼容性问题的必加标签 |
| `regression` | 若问题由版本升级引入（如 v4.27.x）则应添加 |
| `i18n` / `locale` | 涉及字符编码/输入法兼容性问题（如全角/半角） |

### 置信度校准

| 分析表述 | 置信度上限 |
|----------|------------|
| "已确认"（代码审查） | ≤ 0.85 |
| "已确认"（实际复现） | ≤ 0.95 |
| "已确认"（代码审查 + 实际复现） | ≤ 0.98 |
| "推断"（未验证代码位置） | ≤ 0.80 |

> **核心原则**：声称"已确认"但实际未验证的，置信度应下调 0.1-0.15。

### 重复检测必须包含

```
#X 相似点：[具体相似之处]
#X 差异点：[具体差异之处]
结论：[是/否重复/需进一步核实]
```

禁止仅用"可能是...的重复"而无具体对比依据。

### 代码位置引用

- **日志行号 ≠ 错误发生行**：需向上追溯找到 `event.send()` 等调用点
- 建议表述："检查 main.py 第 X 行附近" 而非 "第 X 行"

### 修复方案需提供

1. **修复前后代码对比**（最小化示例）
2. **替代方案**（至少 2 种，便于评审选择）
3. **副作用评估**（如全角转半角是否影响刻意使用的场景）

## 四、代码模式观察

| 模式 | 关注点 | 建议 |
|------|--------|------|
| 两处相同错误 | 可能暗示复制粘贴或同时引入 | 审查时应 `grep` 全局同类调用 |
| 配置驱动型项目 | 用户输入多样性易被忽略 | 需考虑大小写、全角/半角、空格等 |
| 硬编码字符串匹配 | 缺乏容错性 | 建议在入口层增加输入规范化 |
| 最小改动修复 | 粒度控制正确 | 但需确认是否引入新的不一致 |

---

## 五、审查输出标准

### PR 审查结论应包含

1. **框架兼容性声明**：框架名称 + 精确版本号 + API 变更类型
2. **影响范围评估**：影响版本范围 vs 不影响版本范围
3. **未覆盖范围说明**（quick 策略必须）："本次仅验证修复点，未做全量回归"
4. **回归测试建议**：是否需要补充单元测试

### Issue 分析结论应包含

1. **根因**：明确是"推断"还是"已确认"
2. **标签**：至少包含 bug/enhancement + 相关领域标签
3. **置信度**：明确说明验证方式（代码审查/实际复现）
4. **标题改写**：保留 `[类型][优先级]` 元信息 + 技术关键词

---

## 六、核心改进方向（优先级排序）

1. **框架兼容性规范**：版本精确性 + 标签完整性 + 全局扫描
2. **置信度校准**：严格区分"推断"与"确认"
3. **quick 策略边界**：明确标注覆盖范围
4. **输入规范化**：配置驱动型项目增加多样性考虑
5. **重复检测对比**：提供具体相似点/差异点
