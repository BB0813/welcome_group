## 1. 框架 API 变更审查规范

### 必须检查项
| 检查项 | 要求 |
|--------|------|
| 框架版本号 | 精确到 patch（如 v4.27.2），避免 `v4.27.x` 模糊表述 |
| API 签名变更 | 明确参数类型变化（list→MessageChain） |
| 全局扫描 | quick 策略也需说明是否执行 grep 全项目搜索 |
| 向后兼容性 | 评估是否需要版本判断或 fallback |
| **注入行为扩散评估** | 框架自动注入组件时，评估触发范围（哪些事件类型受影响） |
| **版本影响边界说明** | 明确说明从哪个框架版本开始受影响 |

### Quick 策略边界
```
策略   | 验证范围              | 结论要求
-------|----------------------|------------------
quick  | 修复点+直接影响       | 必须注明"未做全量回归"
full   | 修复点+间接影响+模式  | 提供回归测试建议
```

### 框架 API 绕过修复审查清单
```
框架 API 变更审查检查清单
├── 版本号精确性
│   ├── [x] 精确到 patch (v4.27.2)
│   └── [ ] 说明影响起始版本
├── 全局影响评估
│   ├── [ ] grep event.send() 调用点
│   ├── [ ] grep MessageChain 构建点
│   └── [ ] 评估框架注入行为的触发范围
├── 兼容性策略
│   ├── [x] fallback 机制
│   ├── [ ] 版本判断逻辑（如需要）
│   └── [ ] API 能力检查（hasattr）
└── 测试覆盖
    └── [ ] 建议补充框架版本兼容性测试
```

## 2. Issue 分析标签体系

### 必选标签（框架升级问题）
```markdown
bug                          # 置信度 0.95
framework-compatibility      # 置信度 0.8（仅限插件适配框架场景）
regression                   # 置信度 0.85（v4.27.2 版本回归，框架升级问题强制要求）
needs-review                 # 置信度 0.6（待官方确认）
```

### 外部依赖/框架问题必加标签
```markdown
external-dependency          # 置信度 0.95（问题根因明确不在本仓库）
regression                   # 置信度 0.6（如有版本号变化）
needs-info                   # 置信度 0.5（缺少框架侧代码证据）
```

### 标签使用原则
- `enhancement` 不适用于运行时错误
- 框架升级问题**必须添加 `regression` 标签**
- `framework-compatibility` 仅用于"本仓库需适配框架变化"场景，框架自身 bug 用 `external-dependency`
- 标签置信度需与证据明确程度匹配

## 7. 核心经验

| 场景 | 关注要点 |
|------|----------|
| 框架 API 变更 | 版本号精确性、向后兼容性、潜在扩散风险 |
| 批量相同修改 | 暗示复制粘贴或同时引入，评估能否重构 |
| Quick 审查 | 明确边界，避免"看起来没问题"的模糊结论 |
| 测试代码差异 | 框架升级时测试代码也可能受影响 |

## 9. PR 描述一致性验证

### 触发条件
当 PR 描述声明"移除 X"或"添加 X"时，必须验证代码是否与描述一致。

### 验证步骤
```
1. grep -n "目标符号" 文件   # 定位所有使用点
2. 检查 import 语句          # 确认是否在导入列表
3. 分析使用场景              # 是否确实需要（vs 可用替代方案）
4. 对照 PR 描述              # 是否与声明的变更一致
```

### 危险信号
- 描述说"移除"但代码仍在使用 → 高风险信号，可能是多轮修改未同步
- 描述与代码矛盾时 → 超出了单纯功能问题的范畴，需深入分析

## 11. Fallback 健壮性审查

### 审查清单
```python
# 多层 fallback 策略检查
1. 验证每个路径的可用性假设
2. 检查 None 时的行为是否有日志记录
3. 确认 fallback 分支真的可用（而非"理论上可用"）

# getattr(..., None) 的审查重点
1. default 值为 None 时，后续是否有显式检查？
2. None 时是否有日志记录？
3. 是否有其他 fallback 路径？
```

### 常见模式
```
多层 Fallback 策略
├── 路径 1: bot.send_group_msg()     ← 绕过框架
├── 路径 2: event.send()            ← 框架兼容
└── 路径 3: logger.warning()        ← 静默降级
```
