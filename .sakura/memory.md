# Code Review 经验沉淀

累计反思 10 次

## 一、Issue 分析底线原则

| 原则 | 说明 |
|------|------|
| **信息不足 ≠ 可以猜测** | Issue 缺少复现步骤/日志/环境时，应请求补充而非强行分析 |
| **区分根因类型** | 代码 bug → high，配置问题 → medium/ low，用户失误 → question |
| **解析失败 ≠ 零产出** | 应基于错误文本做最大努力推断，保留推断性建议 |
| **置信度反映信息完整度** | Issue 信息越少，置信度上限越低（无信息时上限 0.6） |

## 二、分类与优先级规范

**分类准确性**：
- 运行时异常（AttributeError/TypeError）→ `bug`
- 框架兼容性/API 变更 → `bug` + `framework-compatibility`
- 用户描述模糊/缺少诊断 → `bug` + `needs-info`

**优先级校准**：
- 核心功能完全失效 → 考虑升为 critical
- 诊断信息缺失的 bug → 置信度降至 0.5-0.7
- 模板变量不匹配等可快速定位 → 可标记 `good-first-issue`

## 三、标签推荐规范

| 标签 | 适用场景 | 置信度建议 |
|------|----------|------------|
| `bug` | 运行时异常/功能失效 | 0.80-0.95 |
| `needs-info` | 缺少日志/复现步骤/环境信息 | — |
| `needs-investigation` | 根因不明，需深入排查 | — |
| `framework-compatibility` | 涉及第三方 API 兼容性 | — |
| `good-first-issue` | 问题路径清晰、代码量小 | 0.7 |
| `question` | 可能是用户操作/配置问题 | — |
| `regression` | 新引入的 bug | — |

## 四、可行性判断规范

**必须包含**：
1. **根因定位**：具体到文件名/行号/方法名
2. **文档验证状态**："已查/待查 AstrBot API 文档"
3. **修复路径**：2-3 个可行方向（含优先顺序）
4. **信息缺口清单**：需要用户补充什么信息

**依赖第三方 API 的 bug**：
```
必须补充：
- 已查阅框架版本：v4.27.x
- API 签名变更确认：是/否/待查
- 兼容性风险：是否影响其他版本
- Workaround：降级/配置调整等临时方案
```

## 五、重复检测规范

**禁止**：
- 仅凭"标题相似"判断重复
- 仅凭"关键词匹配"判断重复

**必须**：
- 对比具体错误类型/调用栈
- 给出"相似点/差异点"分析
- 无法确认时标记"需进一步核实"

## 六、标题改写规范

**保留**：`[bug][high]` 等显式元信息
**添加**：核心错误描述（便于搜索）
**避免**：过度改写或完全无建议

```
✅ [bug][high] 消息发送失败: list object has no attribute 'chain'
✅ [bug] 入群欢迎消息未发送问题排查
❌ bug（无建议）
```

## 七、特定类型 Issue 分析模板

**运行时异常类（如 AttributeError）**：
```
1. 提取错误类型：AttributeError → 类型错误
2. 定位代码位置：文件:行号
3. 推断根因：
   - list 调用链方法 → 模板渲染返回类型错误 / LLM 返回格式不符
   - 检查 .get() vs [] 取值
4. 补充需求（自动追问）：
   - 触发事件的完整类型（入群/退群/被踢）？
   - 涉及的配置模板内容？
   - 是否开启 LLM 生成？
```

**功能失效类（如不发欢迎语）**：
```
1. 优先验证：用户是否正确启用了功能（/welcome on）
2. 其次验证：Bot 是否正常接收事件（检查事件过滤器）
3. 最后排查：模板/变量等细节
4. 诊断引导：需要用户提供日志/配置状态
```

## 八、置信度校准指南

| 分析中出现的表述 | 置信度上限 |
|------------------|-----------|
| "可能""大概是""也许是" | ≤ 0.80 |
| "未找到""待验证" | ≤ 0.75 |
| 信息极度匮乏（仅一句话） | ≤ 0.60 |
| 根因明确、有文档支持 | 0.90-0.95 |

## 九、项目特有关注点（welcome_group）

- 配置驱动型项目 → 很多"bug"可能是用户配置错误
- 单文件简单架构 → 模板变量不匹配等问题容易排查
- LLM 集成有 fallback → 需确认欢迎语生成失败时的降级机制
- AstrBot 框架兼容性 → 检查 `event.send()` 参数契约是否变更
- 配置字段前缀式约定 → 注意 leave_message/kick_message 等分支判断

## 十、审查修复分支规范

**发现分支问题时**：
- 结论直接给"不适用"，无需逐条批评
- 除非后续需提交正式 review，否则保持简洁
