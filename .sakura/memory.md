## 核心经验

### 1. 框架 API 变更审查规范

涉及框架 API 变更时（如 AstrBot）必须明确以下内容：

| 检查项 | 要求 |
|--------|------|
| **框架版本号** | 精确到 patch，如 `v4.27.2`，避免 `v4.27.x` 范围过宽 |
| **API 签名变更** | 确认参数契约变化（类型、返回值） |
| **向后兼容性** | 评估是否需要版本判断逻辑 |
| **全局调用扫描** | 使用 grep 检查项目中是否存在同类问题 |
| **MessageChain 传入验证** | 追踪 message_list 构建逻辑，确认类型一致性 |

**模板**：
```markdown
修复涉及 AstrBot 框架 API：
- 已验证框架版本：X.X.X（必须精确到 patch）
- API 签名变更：已确认/待确认
- 兼容性风险：影响版本范围 X.X.X ~ X.X.X
- 全局扫描：已执行/未执行（必须注明）
- MessageChain 类型验证：已确认/待验证
```

### 框架兼容性修复专项检查清单

```markdown
### 框架兼容性修复审查清单
- [ ] 确认框架版本号（精确到 patch）
- [ ] 确认 API 变更的 scope（影响哪些方法）
- [ ] 评估向后兼容性（是否需要版本判断）
- [ ] 验证 fallback 机制（如有）
- [ ] 全局扫描：grep 同类调用，确认无遗漏

### MessageChain 传入验证
- [ ] message_list 构建路径追踪
- [ ] 确认 message_list 元素类型符合预期
- [ ] 检查是否有条件分支返回非 list 类型

### Reply 组件 id 类型检查
- [ ] grep 关键词：`Reply(` 或 `MessageChain([Reply`
- [ ] 确认 id 字段来源（框架生成/项目代码赋值）
- [ ] 验证 id 类型应为 int 而非 str
```

### 2. Quick 策略边界定义

| 策略 | 验证范围 | 必须在结论中注明 |
|------|----------|------------------|
| quick | 修复点 + 直接影响范围 | "未做全量回归" |
| full | 修复点 + 间接影响 + 模式分析 | "含回归建议" |

**关键原则**：quick 审查应在结论中明确标注"仅覆盖变更范围，未进行全局扫描"。

### 3. Issue 分析中的信息一致性处理

当 Issue 存在明显信息不一致（如标题写 `{{at}}`，正文写 `｛at｝`）时，应：
1. **明确指出不一致**
2. **要求用户确认实际使用的语法**
3. **不要自行假设哪种是"正确"的**

### 4. enhancement 类 Issue 分析要点

| 检查项 | 要求 |
|--------|------|
| **标签完整性** | 优先考虑 `feature-request`、`configuration` 标签 |
| **可行性判断** | 信息匮乏 ≠ 分析空缺，必须给出推测性实现方向和预期配置结构 |
| **重复检测** | 必须具体对比（相似点/差异点），避免"可能"等模糊措辞 |
| **good-first-issue 置信度** | 需求细节不足时置信度应降低（如 0.4） |
| **回退机制说明** | 全局配置需明确与独立配置的优先级关系 |

### 5. 模板变量类 Issue 分析要点

```
□ 确认代码中定义的正则表达式模式
□ 确认用户实际使用的占位符格式
□ 区分"代码 bug"还是"文档误导用户"
□ 检查大小写敏感性（如 {At} vs {at}）
□ 检查全角/半角兼容性（如 ｛at｝ vs {at}）
□ 列出替代修复方案（规范化 vs 条件兼容）
```

### 6. 配置驱动型项目审查关注

| 关注点 | 说明 |
|--------|------|
| 用户输入多样性 | 大小写、全角/半角、空格等需规范化 |
| 硬编码字符串匹配 | 缺乏容错性，建议增加容错层 |
| 模板语法文档 | 需明确说明占位符格式要求 |
| 向后兼容性 | 新增全局配置需考虑现有独立配置的迁移 |
| 输入验证层 | 是否需要增强用户输入验证/规范化处理 |

### 7. Issue 分析置信度校准

| 分析表述 | 置信度上限 | 说明 |
|----------|------------|------|
| "已确认" + 实际验证代码 | 0.9 | 验证充分 |
| "已确认" + 未验证代码 | 0.8 | 应改为"推断位置" |
| "待验证" + 推测 | 0.7 | 需补充验证步骤 |
| 代码审查确认（非实际复现） | -0.1 | 置信度应适度降低 |

## 标签推荐规范

### 必须添加的场景

| 场景 | 标签 | 置信度 |
|------|------|--------|
| 框架 API 变更问题 | `framework-compatibility` | 0.8 |
| 字符编码/输入法兼容性 | `i18n` 或 `locale` | - |
| 版本升级引入的回归 | `regression` | 0.85 |
| 涉及框架兼容性需官方确认 | `needs-review` | 0.6 |
| 用户语法不明确 | `needs-info` | - |
| 明确的新功能请求 | `feature-request` | - |
| 配置系统相关的功能增强 | `configuration` | - |

### Issue 重复检测模板

```markdown
重复检测：
- #XX 摘要：[引用标题和核心问题描述]
- 相似点：...
- 差异点：...
- 重复置信度：0.XX
- 结论：[是/否/可能重复，建议...]
```

### Comments 置信度标注规范

```markdown
[comment]: 根据项目知识文档推断（置信度：0.7）
         建议验证：是否可补充相关代码路径说明？
```

**原则**：依赖文档而非代码验证时，应降低置信度标注。
