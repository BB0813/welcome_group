## 核心经验

### 1. 框架 API 变更审查规范

涉及框架 API 变更时（如 AstrBot）必须明确以下内容：

| 检查项 | 要求 |
|--------|------|
| **框架版本号** | 精确到 patch，如 `v4.27.2`，避免 `v4.27.x` 范围过宽 |
| **API 签名变更** | 确认参数契约变化（类型、返回值） |
| **向后兼容性** | 评估是否需要版本判断逻辑 |
| **全局调用扫描** | 使用 grep 检查项目中是否存在同类问题 |

**模板**：
```markdown
修复涉及 AstrBot 框架 API：
- 已验证框架版本：X.X.X
- API 签名变更：已确认/待确认
- 兼容性风险：影响版本范围 X.X.X ~ X.X.X
- 全局扫描：已执行/不适用
```

### 2. Quick 策略边界定义

| 策略 | 验证范围 | 必须在结论中注明 |
|------|----------|------------------|
| quick | 修复点 + 直接影响范围 | "未做全量回归" |
| full | 修复点 + 间接影响 + 模式分析 | "含回归建议" |

**关键原则**：quick 审查应在结论中明确标注"仅覆盖变更范围，未进行全局扫描"。

### 3. Issue 分析中的信息一致性处理

当 Issue 存在明显信息不一致（如标题写 `{{at}}`，正文写 `｛at｝`）时，应：
1. **明确指出不一致**
2. **要求用户确认实际使用的语法**
3. **不要自行假设哪种是"正确"的**

### 4. 模板变量类 Issue 分析要点

```
□ 确认代码中定义的正则表达式模式
□ 确认用户实际使用的占位符格式
□ 区分"代码 bug"还是"文档误导用户"
□ 检查大小写敏感性（如 {At} vs {at}）
□ 检查全角/半角兼容性（如 ｛at｝ vs {at}）
```

### 5. 配置驱动型项目审查关注

| 关注点 | 说明 |
|--------|------|
| 用户输入多样性 | 大小写、全角/半角、空格等需规范化 |
| 硬编码字符串匹配 | 缺乏容错性，建议增加容错层 |
| 模板语法文档 | 需明确说明占位符格式要求 |

### 6. Issue 分析置信度校准

| 分析表述 | 置信度上限 | 说明 |
|----------|------------|------|
| "已确认" + 实际验证代码 | 0.9 | 验证充分 |
| "已确认" + 未验证代码 | 0.8 | 应改为"推断位置" |
| "待验证" + 推测 | 0.7 | 需补充验证步骤 |

## 标签推荐规范

### 必须添加的场景

| 场景 | 标签 |
|------|------|
| 框架 API 变更问题 | `framework-compatibility` |
| 字符编码/输入法兼容性 | `i18n` 或 `locale` |
| 版本升级引入的回归 | `regression` |
| 涉及框架兼容性需官方确认 | `needs-review` |
| 用户语法不明确 | `needs-info` |
