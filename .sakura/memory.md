# 代码审查经验积累

> 累计反思 23 次

## 1. 框架 API 变更审查规范

### 必须检查项
| 检查项 | 要求 |
|--------|------|
| 框架版本号 | 精确到 patch（如 v4.27.2），避免 `v4.27.x` 模糊表述 |
| API 签名变更 | 明确参数类型变化（list→MessageChain） |
| 全局扫描 | quick 策略也需说明是否执行 grep 全项目搜索 |
| 向后兼容性 | 评估是否需要版本判断或 fallback |

### Quick 策略边界
```
策略   | 验证范围              | 结论要求
-------|----------------------|------------------
quick  | 修复点+直接影响       | 必须注明"未做全量回归"
full   | 修复点+间接影响+模式  | 提供回归测试建议
```

## 2. Issue 分析标签体系

### 必选标签（框架升级问题）
```markdown
bug                          # 置信度 0.95
framework-compatibility      # 置信度 0.8
regression                   # 置信度 0.85（v4.27.2 版本回归）
needs-review                 # 置信度 0.6（待官方确认）
```

### 标签使用原则
- `enhancement` 不适用于运行时错误
- 框架升级问题**必须添加 `regression` 标签**
- 标签置信度需与证据明确程度匹配


## 4. 代码风格规范

### 字符串格式化
```python
# ✅ 统一使用 f-string
f"错误信息: {e}"

# ❌ 避免 + 拼接
"错误信息: " + str(e)
```

### 类型显式转换
- `user_id` 等字段统一做 `int()` 转换
- `message_list` 构建后验证是否为 list 类型

## 5. Comments 置信度标注

```markdown
# 当前（问题）

# 建议（正确）
[comment]: 根据项目知识文档推断（置信度：0.7）
         建议验证：[具体代码位置]
```

## 7. 核心经验

| 场景 | 关注要点 |
|------|----------|
| 框架 API 变更 | 版本号精确性、向后兼容性、潜在扩散风险 |
| 批量相同修改 | 暗示复制粘贴或同时引入，评估能否重构 |
| Quick 审查 | 明确边界，避免"看起来没问题"的模糊结论 |
| 测试代码差异 | 框架升级时测试代码也可能受影响 |
