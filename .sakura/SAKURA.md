# 项目概述：welcome_group

## 1. 项目简介

`welcome_group` 是一个用于 AstrBot 的群聊管理插件，可在群成员入群、主动离群或被管理员移出时，自动发送自定义提醒消息，并支持通过 LLM 自动生成消息内容。

## 2. 技术栈

- **开发语言**：Python
- **运行平台**：AstrBot 插件系统
- **配置方式**：
  - JSON 配置文件：用于保存默认消息、群组独立配置、LLM 开关等
  - `_conf_schema.json`：用于 AstrBot 控制台配置界面
- **AI 能力**：
  - 支持接入 AstrBot 已配置的 LLM Provider
  - 可通过命令选择指定 LLM Provider 或使用当前聊天上下文中的模型
- **开源协议**：GNU AGPLv3

## 3. 项目结构

- `main.py`  
  插件核心逻辑文件，负责处理群成员变动事件、命令解析、配置读写、消息模板渲染以及 LLM 调用。

- `_conf_schema.json`  
  AstrBot 插件配置 Schema 文件，用于定义插件在控制台中的配置项展示和校验规则。

- `metadata.yaml`  
  插件元信息文件，供 AstrBot 加载插件时识别插件名称、版本、作者等信息。

- `README.md`  
  项目说明文档，包含功能介绍、命令列表、安装方式、配置示例和依赖说明。

- `LICENSE`  
  项目开源协议文件，使用 GNU Affero General Public License v3。

- `.gitignore`  
  Git 忽略规则文件，用于排除运行缓存、临时文件或本地配置等不应提交的内容。

- `.sakura/`  
  项目辅助目录，包含文档、记忆和规则等内容，可能用于开发工具或自动化辅助系统。

## 4. 开发约定

- **单插件主文件结构**  
  当前项目以 `main.py` 作为主要实现入口，逻辑集中，适合小型 AstrBot 插件维护。新增功能应优先围绕该文件的事件监听、命令处理和配置管理模块扩展。

- **配置驱动设计**  
  插件通过默认配置和 `groups` 字段实现群组级独立设置。开发时应保持配置字段向后兼容，避免破坏已有用户的 `config.json`。

- **群组隔离原则**  
  每个群的入群欢迎、离群通知、退群通知均可独立启用和配置。新增功能也应尽量支持按群组单独控制，避免全局配置影响所有群。

- **命令统一前缀**  
  所有用户命令均以 `/welcome` 开头，子功能通过二级参数区分，例如 `leave`、`kick`、`llm`。后续新增命令建议继续沿用该前缀体系，保持使用体验一致。

- **模板变量约定**  
  消息模板支持 `{at}`、`{time}`、`user_id` 等变量。新增模板变量时应在 README 中同步说明，并保证旧模板仍可正常渲染。

- **LLM 功能可选**  
  LLM 自动生成消息是可选能力，默认关闭。相关逻辑应在未配置 Provider 或模型调用失败时安全降级，避免影响基础欢迎/通知功能。

- **依赖 AstrBot 运行时**  
  项目本身未体现独立 Web 服务或 CLI 程序形态，主要依赖 AstrBot 提供事件、消息发送和 LLM Provider 管理能力。开发和测试应在 AstrBot 插件环境中进行。

- **文档同步维护**  
  README 已包含完整命令、配置和安装说明。后续修改命令、配置字段或行为逻辑时，应同步更新 README 和配置 Schema。

- **测试命令与生产命令 1:1 对齐**  
  测试命令（如 `/welcome test`、`leave_test`、`kick_test`）必须完整复用真实事件路径的模板渲染、消息组件与 LLM 提示构造，禁止"简化版"逻辑；抽取公共函数时所有差异化维度（语气词、日志标签、错误文案）都必须参数化。

- **空模板防御**  
  事件处理器在读取模板/配置后必须做空值校验，避免向群内发送空白消息；配置读取优先使用 `[]` 而非 `.get()`，让损坏快速暴露。

- **LLM 调用安全降级**  
  LLM 自动生成消息必须具备 fallback（默认模板）+ 用户反馈（告知失败原因），严禁静默吞掉异常；同时需考虑权限校验与防滥用，避免普通成员刷屏或消耗 LLM 配额。

- **重构时验证行为等价性**  
  重构提交不仅要关注代码组织变化，更要保证对外可观测行为不变；特别留意 `.get()` vs `[]`、字符串字面量、日志标签、提示语措辞是否被无意消除。

- **静态检查建议**  
  建议启用 ruff `F541`（f-string 必须包含占位符）等轻量 lint 规则，减少冗余 f-string 这类高频轻量问题的人工审查负担。

## 5. 项目审查与质量规范

基于 PR #29 与 Issue #28/30/31 的反思，已沉淀以下项目级规范要点：

| 类别 | 规范要点 |
|------|---------|
| 命令命名 | AstrBot `command_group` 不支持嵌套，所有命令统一挂在 `/welcome` 下，子功能通过命令名后缀区分（如 `leave_test`、`kick_test`） |
| 配置字段 | 消息字段统一采用"事件类型前缀"模式（`leave_message`、`kick_message`），新增事件类型需沿用 |
| Handler 重复 | 超过 20 行的相似 handler 必须考虑抽取公共辅助函数；本次 30 行级别重复已触发抽象 |
| 测试命令语义 | 必须 1:1 复现真实事件路径；可选支持 `@user` 指定测试对象；消息应标注"测试"以免混淆 |
| Issue 分析 | 尊重标题中的显式元信息（`[feature]`、`[low]`）；功能增强类至少给出 `feature`/`enhancement` 等基础标签 |
| 增量审查 | 必须在开头列出"上轮意见 → 本轮修复"对照表，并对被修改函数做全量调用点扫描 |

### 5.1 Issue 分析质量规范

| 维度 | 规范要点 |
|------|---------|
| **分类准确性** | 运行时异常（如 AttributeError/TypeError）→ `bug`；配置驱动系统的"bug"需先确认是代码缺陷还是用户配置问题 |
| **优先级校准** | 核心功能完全失效应考虑 `critical` 而非 `high`；信息不足的 Issue 优先考虑 `medium` 或 `low` |
| **标签推荐** | 解析失败 ≠ 放弃推荐，应基于错误文本做最大努力推断；信息不足时必须加 `needs-info` |
| **置信度校准** | 分析中出现"可能""未找到""待验证"时，置信度上限不超过 0.85；Issue 信息极度匮乏时降至 0.5-0.6 |
| **可行性判断** | 必须包含"已确认/待查"状态；非本代码库错误必须给用户侧操作指引 + workaround |
| **重复检测** | 不能仅靠标题相似度，需对比根因模式 + 具体错误信息；给出"相似点/差异点"对照 |
| **诊断引导** | 对信息不足的 Issue 应补充"需用户提供的诊断信息"清单（日志、配置、环境） |

### Issue 分析标签扩展规范

**enhancement 类 Issue 标签推荐**：
| 标签 | 适用场景 | 置信度建议 |
|------|---------|-----------|
| `enhancement` | 明确的功能增强请求 | 0.9-0.95 |
| `feature-request` | 明确的新功能请求，提高可见性 | 0.8-0.85 |
| `configuration` | 配置功能增强（配置驱动型项目优先考虑） | 0.75-0.8 |
| `good-first-issue` | 需求细节不足时置信度应降低 | 0.4-0.6 |

**i18n/locale 相关 Issue 标签**：
- 本质是字符编码/输入法兼容性问题（如全角/半角）时，应考虑添加 `i18n` 或 `locale` 标签

**可行性判断强制要求**：
- 信息匮乏 ≠ 分析空缺，至少给出推测性实现方向
- 可行性判断可写"基于假设，需确认"，但不能留空

### 5.2 Issue 分析常见根因模式

结合本项目特征，分析时优先验证：

| 根因类型 | 检查项 |
|---------|--------|
| 配置问题 | 是否执行过 `/welcome on`？配置文件中字段值？ |
| 权限问题 | Bot 是否有发送消息权限？事件是否仅群聊有效？ |
| 框架兼容 | 是否为 AstrBot 版本升级导致的 breaking change？检查 `event.send()` 参数契约 |
| 类型错误 | `.get()` vs `[]` 取值差异；模板渲染/LLM 返回值类型是否符合预期 |
| 输入规范化 | 模板变量匹配是否兼容全角/半角？中文输入法的默认行为 |

### 5.3 框架兼容性修复审查规范

涉及 AstrBot 框架 API 变更时，应执行以下专项检查：

| 检查项 | 要求 |
|--------|------|
| 框架版本 | 精确到 patch（如 v4.27.2，而非 v4.27.x） |
| API 签名变更 | 明确参数类型变化（list → MessageChain 等） |
| 全局调用扫描 | **必须说明搜索关键词和结果**，使用 grep 检查项目中是否存在同类型问题 |
| 向后兼容性 | 评估是否需要版本判断或 fallback |
| 注入行为扩散评估 | 评估框架自动注入行为的触发范围（哪些事件类型受影响） |
| 验证方式 | 明确是"代码审查确认"还是"实际复现确认" |

**quick 策略边界**：
- 仅覆盖修复点及直接影响范围
- 结论中应注明"未做全局回归"
- 如需 full review 应作为前置条件
- **框架 API 变更时**：必须明确回答"全局扫描是否执行"，边界外问题在结论中显式声明

**AstrBot 兼容性声明规范**：
```markdown
修复涉及 AstrBot 框架 API：
- 已验证框架版本：X.X.X（精确到 patch）
- API 签名变更：已确认/待确认
- 兼容性风险：影响版本范围 X.X.X ~ X.X.X
- 验证方式：代码审查/实际复现
- 全局扫描状态：已执行，确认以下位置使用 bot.send_group_msg() 或已修复
  - [列出所有调用点]
```

### PR 描述一致性验证规范

当 PR 描述声明"移除 X"或"新增 Y"时，审查必须验证实际代码是否匹配：
- 执行 `grep -n "X"` 确认使用点是否真的已移除
- 对比 PR 描述与代码实现是否存在矛盾
- 警惕"声明与代码不一致"的高风险信号

**发现矛盾时的处理**：
1. 明确指出矛盾点
2. 评估是否影响审查结论
3. 要求作者澄清或修正描述

### 5.4 框架问题 Issue 分析规范

当 Issue 根因明确在 AstrBot 框架而非本仓库时，应采用以下规范：

| 维度 | 规范要点 |
|------|---------|
| **标签必加** | `external-dependency`（外部依赖）、`needs-upstream-fix`（等待上游修复） |
| **回归标签** | 涉及框架版本升级时，添加 `regression` 标签 |
| **责任边界** | 明确区分"框架 bug"与"框架兼容性问题"，前者不用 `framework-compatibility` |
| **缓解方案** | 必须提供用户侧 workaround（如手动安装、降级版本） |
| **上游渠道** | 指引用户向 AstrBot 主仓库提 Issue |

**框架问题分析模板**：
```markdown
### 责任归属
根因位置：[框架]/[插件]/[用户配置]

### 上游渠道
AstrBot 主仓库 Issue 链接（待用户确认）

### 插件侧应对
- 短期：[说明情况，等待框架修复]
- 长期：[考虑内置 fallback 方案]

### 用户引导
- [手动安装 zip 包]
- [降级框架版本建议]
```

### 5.5 框架兼容性 Issue 分析标签规范

当 Issue 涉及 AstrBot API 变更时，必须添加以下标签：

| 标签 | 适用场景 | 置信度建议 |
|------|---------|-----------|
| `framework-compatibility` | AstrBot 版本升级导致的 API 行为变化 | — |
| `regression` | 可确认是某版本升级引入的回归（**框架版本升级问题必须添加**） | 高置信度时 |
| `needs-review` | 需官方确认 API 变更范围 | — |
| `external-dependency` | 问题根因明确在框架侧，非本仓库代码 | 0.95 |
| `needs-upstream-fix` | 插件侧无法独立解决，需上游修复 | 0.9 |

**置信度校准补充**：
- 声称"已确认"但未验证代码 → 置信度上限 0.80
- 缺少版本对比信息 → 置信度降至 0.7-0.8
- 应明确标注验证方式（代码审查/实际复现）
- 错误堆栈中的具体信息（如 `'a76d66d61044464c9b92fde4cb0ddef3'`）应被引用作为证据

## 6. 关键经验教训

- **重构的最大风险是行为回归**，而非新 bug；审查时应主动比对前后语义差异。
- **测试命令不等于简化逻辑**，核心价值在于 1:1 复现真实路径，简化即失效。
- **配置驱动系统的 `.get()` 是温和杀手**：配置损坏时表现为"功能正常但内容空白"，比 `KeyError` 更难排查。
- **文档同步是 PR 完整性的硬指标**，建议在 PR 模板加入"修改命令时同步 README"的勾选项。
- **短文本 Issue 不能仅凭字数判断价值**，需求明确即可，无需长篇描述。
- **机器人插件需特别关注运行环境**：命令是否仅群聊有效、权限控制、上下文模拟、是否误触发真实业务逻辑。
- **Issue 分析信息不足时必须追问**：不能强行分析，更不能因解析失败而放弃所有维度的建议。
- **区分代码缺陷 vs 用户配置问题**：配置驱动系统中很多"bug"源于用户未正确配置，此类 Issue 应标记 `needs-info` 而非 high。
- **诊断引导是 Issue 分析的标配**：对信息不足的 Issue 应主动列出"需要用户补充的信息清单"。
- **框架 API 变更需明确版本范围**：应精确到 patch（如 v4.27.2），避免"v4.27.x"这类宽泛表述。
- **quick 策略需设置明确边界**：审查范围外的问题应在结论中标注，避免"看起来没问题"的模糊结论。
- **输入规范化遗漏是配置驱动型项目的常见问题**：全角/半角、大小写、空格等用户输入多样性需要考虑。
- **重复检测必须具体**：对比维度包括标题/功能描述/实现方式，无法确认时明确写"需维护者核实"，避免"可能"这类模糊措辞。
- **框架 API 变更需全局扫描**：修复 A 处时思考"是否有其他调用点使用相同模式"，quick 审查需在结论中标注扫描状态。
- **"有意为之"的表述需谨慎**：依赖文档而非代码验证时应降低置信度标注，建议格式：`[推测/推断/待验证] + 置信度`。
- **错误堆栈信息应被引用**：Bug 分析时引用具体错误信息作为证据，提升分析说服力。
- **框架版本回归问题必须添加 `regression` 标签**：与 `framework-compatibility` 配合使用，标注回归风险。
- **框架绕过式修复需评估长期影响**：绕过框架直接调用协议端时，暗示框架行为变化具有扩散性，应评估注入行为的触发范围。
- **PR 描述与代码不一致是危险信号**：当描述说"移除 X"但代码仍在使用时，需警惕多轮修改未同步或意图与实现偏差。
- **外部依赖问题需标准化处理**：框架 bug 不同于框架兼容性问题，应使用 `external-dependency` 标签并提供用户 workaround。
